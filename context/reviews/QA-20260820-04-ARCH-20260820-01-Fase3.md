## F. Hallazgos priorizados

### F-3 — Cierre DOCUMENTAL del endpoint `/resolve` sin guard de auth de código

**Severidad:** P2 (documentado como P3 en QA Fase 1; la handoff §12 Fase 3 requiere cerrar antes de conectar Events; el cierre es **válido** pero **no implementa** un guard de código).

- **Evidencia:** `backend/app/api/v1/calibration.py:783-829` (líneas +45). El cierre es **un bloque de comentario** que documenta:
  1. No existe middleware de auth global en `main.py` (sólo `CORSMiddleware`).
  2. `calibration_router` se monta sin prefijo `/api/v1/admin/` (main.py:2007).
  3. Endpoint solo-lectura, no expone secretos (validadado por `TestNoSecretsExposed`).
  4. Events NO consume `/resolve` por fetch desde el navegador; consume el server action `getPublishedCalibrationForEventTest` (frontend/src/actions/calibration-v3.actions.ts:750), que corre server-side en Next.js, lee Prisma directamente, y NO replica la lógica del adaptador V1/V2.
  5. Añadir un guard directo (e.g. `_require_superadmin` con headers `x-ami-*`) **requiere decidir el rol a exigir** (SUPERADMIN vs ADMIN vs autenticado), lo que toca ADR §7.1 **pendiente de Frank** — no se infiere (handoff §11).
  6. La decisión de añadir auth directa al endpoint se difiere a ADR §7.1 (pendiente Frank), a implementar cuando el rol de publicación esté confirmado.

- **Análisis GEMINI (independiente):**
  - **Verificación de las afirmaciones del bloque:** todas correctas. `main.py` líneas 125-138 sólo registran `CORSMiddleware`. `main.py:2005-2007` monta `calibration_router` sin prefijo `/api/v1/admin/`. `grep -rn "Depends(" backend/app/api/v1/` confirma que ningún router de `app/api/v1/` usa `Depends(` (las únicas coincidencias son los comentarios del propio bloque F-3). Verifico por lectura que `getPublishedCalibrationForEventTest` NO hace `fetch('/api/v1/calibration/resolve')` — sólo lee Prisma (calibration-v3.actions.ts:759-770).
  - **¿Es el patrón existente suficiente?**
    - **A favor (suficiente mientras Fase 7 no llegue):** el endpoint es solo-lectura (`resolve_calibration` no muta DB; verificado en QA Fase 1 `test_v1v2_adapter_does_not_persist`); no expone secretos (ADR §2.9: contrato V3 no contiene credenciales; `TestNoSecretsExposed` lo verifica); no expone PII clínica (devuelve `prompts`, `fieldDefinitions`, `presentation.schema` — metadata clínica operativa, no datos de pacientes); el consumidor real (server action) corre server-side y hereda la sesión NextAuth del contexto RSC.
    - **En contra (no suficiente si el endpoint queda accesible):** cualquiera con acceso a la red del backend puede hacer `GET /api/v1/calibration/resolve?test_id=<uuid>` y obtener la calibración publicada. No es un secreto violado, pero es **divulgación de configuración de IA** (incluye `canonicalStudyType`, prompts de extracción e interpretación, `presentation.schema`, `fieldDefinitions`). En la mayoría de catálogos esto es aceptable (calibración es data no sensible por diseño), pero en organizaciones con proveedor de IA externo la披露 de `prompts` puede considerarse propiedad intelectual.
  - **¿Es bloqueador para Fase 3?** NO. La handoff §12 dice "Fase 3 debe cerrar F-3 (auth endpoint) antes de conectar Events". El cierre **exigía decidir qué hacer con la auth del endpoint**; SOFIA cumple "decidir y diferir el guard con justificación explícita". El cerramiento es **válido y suficiente para Fase 3**: el consumer real (server action) no toca el endpoint; el endpoint queda documentado como solo-lectura sin secretos, pendiente del ADR §7.1. Eso sí, **no es un fix de código**; es un **governance decision** trasladada a Frank.
  - **¿Es P2 o P3?** Para Fase 3, **P3** (cierre documental proporcionado, riesgo aceptable: endpoint no expuesto al navegador, no secretos, no PII). **Para el conjunto de la SPEC (Fase 7):** debería pasar a **P2** cuando el endpoint pase de tener 0 consumidores a tener ≥1 consumidor real (Fase 4: `prediagnostic.py` lo invocará). En Fase 4 esto se vuelve a tocar; mientras tanto, el patrón server-side action (+ sin fetch navegador) es coherente con la arquitectura actual.

- **Impacto:** mientras el único consumer sea `getPublishedCalibrationForEventTest` (server action), no hay superficie de ataque por navegador. El endpoint backend queda accesible por la red del backend, pero sin auth — consistente con `/upload`, `/snapshots` y `/test/{id}/results` del mismo módulo (no es regresión introducida por Fase 3).

- **Riesgos residuales:**
  - Si en Fase 4 `prediagnostic.py` empieza a invocar `/resolve` con su propio contexto de auth, el patrón debe replicarse (consultar `getServerSession` antes de llamar al endpoint, o aceptar el endpoint como interno por convención de despliegue).
  - Si Frank decide exigir auth a nivel backend (no sólo server action), la implementación debe entrar antes de Fase 4 (cuando `prediagnostic.py` consuma `/resolve`).

- **Condición de cierre:** **F-3 SE CIERRA DOCUMENTALMENTE en Fase 3** (no requiere fix de código). SOA reabre en **Fase 4** si la decisión ADR §7.1 está tomada Y `prediagnostic.py` consume el endpoint; mientras tanto, el patrón server action es suficiente. **GEMINI NO bloquea Fase 3 por F-3** — el cerramiento es razonable y proporcionado al riesgo.

- **Owner recomendado:** INTEGRA (decisión ADR §7.1 + reabrir análisis si Fase 4 conecta el endpoint).

### P3 — Mejoras no bloqueantes

#### F-3.1 — Relación entre `currentPublishedVersionId` y `find(status published|disabled)` es defensiva, no contractual

- **Evidencia:** `calibration-v3.actions.ts:783-799`. Si `currentPublishedVersionId` existe, busca por `versionId`; si no, busca la primera `published` o `disabled`. La regla del SPEC §6.2 ("máximo una versión `published`/`disabled`") no está codificada. Si el catálogo viola §6.2 (múltiples `published`), el helper tomaría la primera arbitrariamente.
- **Impacto:** la regla §6.2 la enforce `publishAICalibrationV3` (Fase 2). El helper es consumo: si la DB está bien, la búsqueda es estable. Si la DB tiene más de una `published` (estado inconsistente), el helper cae a "primera encontrada" — comportamiento defensivo y trazable.
