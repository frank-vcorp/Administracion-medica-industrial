## F. Hallazgos priorizados

### P2 — Desviación de contrato / consistencia (no bloqueante, no regresión)

#### F-2.1 — RBAC en `saveAICalibrationV3` demasiado restrictivo vs SPEC §17.2
- **Evidencia:** `calibration-v3.actions.ts:195` usa `isSuperAdmin(role)` que devuelve true solo si `role === 'SUPERADMIN'` (roles.ts:40-42). El JSDoc (actions:182-183) y el mensaje de error (actions:196) dicen "cualquier ADMIN (isAdminLike) puede editar drafts" / "Se requiere rol ADMIN o superior". La SPEC §17.2 propone "`ADMIN` para editar draft, `SUPERADMIN` para publicar".
- **Impacto:** over-restriction (no agujero de seguridad): un ADMIN que según SPEC debería poder editar drafts queda bloqueado. Inconsistencia interna código↔doc↔SPEC. Tests 12 (VENDEDOR→FORBIDDEN) y 27 (ADMIN→FORBIDDEN en publish) codifican el comportamiento restrictivo, "congelando" la desviación. La decisión de rol (ADR §7.1) está pendiente de Frank.
- **Condición de cierre:** INTEGRA decide: (a) cambiar `saveAICalibrationV3` a `isAdminLike` (permitir ADMIN como dice SPEC §17.2) y ajustar tests/mensajes; o (b) actualizar SPEC §17.2 + JSDoc para reflejar SUPERADMIN-only en ambas. Es decisión que toca ADR §7.1 (pendiente Frank) — no resolver por inferencia.
- **Owner recomendado:** INTEGRA (con consulta Frank si toca §7.1).

### P3 — Cosmético / cobertura / code smells

#### F-2.4 — Hash FNV con prefijo `sha256:` engañoso
- **Evidencia:** `calibration-v3.actions.ts:667-676`. `hashString` usa FNV-1a (no criptográfico) pero produce `sha256:fnv-<hex>`. SPEC §5.5 dice "Los campos `*Hash` son `sha256:` del JSON canónico".
- **Impacto:** el prefijo `sha256:` es mentiroso (no es sha256). Los hashes solo son metadata de auditoría (el resolver backend es la fuente runtime), así que el impacto funcional es nulo, pero viola el contrato §5.5 textual y puede inducir a futuros lectores a confiar en la integridad criptográfica.
- **Condición de cierre:** usar Web Crypto `crypto.subtle.digest('SHA-256', ...)` (disponible en Node 18+/Next.js runtime) o cambiar el prefijo a `fnv:`. Recomendado antes de Fase 7 (cuando los hashes se usen para integridad de históricos).
- **Owner recomendado:** SOFIA vía INTEGRA (cleanup L1).

#### F-2.5 — `SupportingReference` definido dos veces (dead code)

## G. Riesgo operativo

- **Seguridad:** sin exposición de secretos. El contrato V3 no contiene credenciales. RBAC: `publishAICalibrationV3` requiere SUPERADMIN (gate real, actions:327-333); `saveAICalibrationV3` también requiere SUPERADMIN (over-restrictivo, ver F-2.1, no agujero). No hay `dangerouslySetInnerHTML` ni exfiltración de datos.
- **Atomicidad:** la transición `tested → published` + `published → superseded` ocurre en **una sola** operación `prisma.medicalTest.update` (actions:596) sobre el documento JSON completo. Prisma garantiza la atomicidad de la escritura del JSON; no pueden coexistir dos `published` porque toda la transición se aplica sobre el mismo documento. **No** hay window de coexistencia. Cumple AC-2.3.
- **Inmutabilidad:** las versiones `published`/`superseded` se "congelan" efectivamente por la serialización `JSON.parse(JSON.stringify(...))` al persistir (`toPrismaJsonValue`, actions:117): al deserializar para la siguiente operación, son copias independientes. No hay `Object.freeze` en memoria, pero la round-trip JSON lo garantiza a nivel de DB. Aceptable; CB-09 sin test (F-2.7).
- **Regresión Fase 1:** `calibration_resolver.py` cleanup F-4 es retrocompatible: `_resolve_v3` acepta `operation_mode` opcional; si es `None` (rama 2 de `resolve`, V3 sin operationMode en options), conserva la inferencia previa. pytest 43/43 verdes. F-1/F-2/F-3 (QA Fase 1) NO se tocaron — correcto (eran fuera de alcance Fase 2).
- **Reversión:** alta. Revertir el árbol de trabajo (los 4 modificados vía `git checkout`, los 2 nuevos son untracked → `rm`) restaura Fase 1. `saveAICalibration`/`saveAICalibrationV2` siguen operativos (solo `@deprecated`). No hay migración de esquema.
- **Observabilidad:** `console.info` con prefijo `[ARCH-20260820-01]` y IDs (testId, versionId, versionNumber, publishedBy) en publish. Suficiente para Fase 2 (F-2.9 para auditoría persistente futura).
