## 1. Resumen de Cambios

### Problema Resuelto
El pipeline de Espirometría tenía dos problemas acoplados que debían implementarse juntos para evitar desalineación:

1. **ARCH-20260516-12** (Extracción Exhaustiva): El contrato `EspirometriaData` solo capturaba 3 campos planos (`fev1`, `fvc`, `fev1_fvc_ratio`). El layout real AMI incluye 6 bloques tabulares: datos demográficos del paciente, metadatos del estudio, condiciones ambientales, tabla de parámetros con LLN, calidad técnica y gráficas. Sin estos bloques, el prediagnóstico carecía de evidencia suficiente (especialmente LLN desde tabla).

2. **ARCH-20260516-13** (Prediagnóstico Coherente): El prediagnóstico podía clasificar incorrectamente como "obstructivo" cuando FEV1/FVC era conservado pero FVC era reducida. Esto viola la Regla A de ATS/ERS 2022. Adicionalmente, el campo `recommendation` podía retornar nulo.

### 3.3 `backend/app/services/ai/prediagnostic.py` (IMPL-20260516-13)

**Prompt `"Espirometria"` endurecido:**
- Jerarquía de evidencia explícita: `parametros (tabla) > LLN > %predicho > flat fields > ATS/ERS genérico`
- **REGLA A**: FEV1/FVC conservado + FVC reducida → NO cerrar como obstructivo (restricción sugestiva, requiere pletismografía)
- **REGLA B**: FEV1/FVC disminuido + FVC reducida → NO simplificar a obstructivo automáticamente (posible mixto)
- **REGLA C**: Repetibilidad negativa → bajar confianza al rango 0.35-0.45
- **REGLA D**: Contradicción entre justificación y summary → emitir `AI_NON_CONCLUSIVE`
- Campo `recommendation` obligatorio, con guardrails (no aptitud, no tratamiento, no dictamen laboral)

**`_check_minimum_params` actualizado (IMPL-20260516-13):**

is_interpretable = extracted_data.get("es_interpretable")
if is_interpretable is None:

    if isinstance(calidad_block, dict):

if completitud == "no_concluyente":

## 6. Riesgos y Observaciones

1. **Calidad block como dict vs objeto**: El método `_check_minimum_params` recibe `extracted_data` como `Dict[str, Any]` (antes de construir `EspirometriaData`). El bloque `calidad` llega como `dict`, lo cual es correcto con `isinstance(calidad_block, dict)`. Si en el futuro se llama con un objeto `EspirometriaData`, el check de calidad no leerá el bloque (se requeriría `calidad_block.es_interpretable`). Se dejó nota en el código.

2. **Regla A en prompt vs en código**: La Regla A (ratio conservado + FVC reducida → no obstructivo) está implementada solo en el prompt al LLM, no como lógica determinista en Python. Esto es correcto para el scope actual (el prediagnóstico es IA + revisión médica), pero se debe monitorear que el LLM respete la regla en producción.

3. **Tests de integración real pendientes**: Los tests con mock verifican el contrato del pipeline pero no pueden detectar si el nuevo prompt hace que el LLM real produzca mejores resultados. Se recomienda prueba con PDFs AMI reales (ver `context/GUIA_PRUEBA_IMPL-20260225-02.md`).
